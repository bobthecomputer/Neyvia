# Neyvia plugin for Claude Code: what was ported

Mod 0.2.0, written against the Claude Code 2.1.293 types (hooks load on 2.1.292). The plugin is a normal Claude Code plugin; nothing in it approves tool calls,
rewrites prompts or reads Claude credentials.

## Parts

- `.mcp.json` + `mcp/neyvia_mcp.py`: MCP server `neyvia` (stdlib Python). Adds `cl` and `cl_describe` to the compatibility startup tools:
  `manual_index`, `manual_load`, `manual_observe`, `manual_run`, `manual_frontier`, `tools_search`, `tools_describe`, `tools_call`, `state`.
  Initialization reads the approved primer and L0 index from the matching backend.
  CL calls enforce this plugin's PORTED scope, including nested procedure observers;
  callers cannot widen it by passing their own scopeTools. Legacy entries remain
  while every managed mutation lacks an equivalent grounded CL observer contract.
  Search lists names/purposes, describe loads one schema, and call sends its exact `neyvia.*` name through
  `POST /api/ui/tools/call` on a loopback Neyvia, signed in with the PC's
  local session. In Claude Code a tool shows as `mcp__plugin_neyvia_neyvia__<name>`.
- `skills/`: the manuals as skills (`neyvia`, `neyvia-pdf`, `neyvia-image-studio`, `neyvia-lab`), generated by
  `scripts/build_claude_plugin_skills.py` (edit CL source in `manuals/cl/`, compile
  with `scripts/cl_compile_manuals.py`, render the views, then run it).
- `hooks/` (the mod, `register.ts` plus small modules): at `session.start` it fetches Neyvia's bootstrap (ETag, cached per
  session) and registers Neyvia's tools as native tools (`mcp__neyvia__*`, deferred by Claude Code behind ToolSearch)
  and the scout/builder/verifier agent roles. The stable Neyvia prompt names exact ToolSearch queries for activity,
  agents, claims, open apps and Night Shift. A cached live summary (at most 600 characters) travels once per turn
  through `prompt.context`; slow provider discovery refreshes separately. Empty or unreachable live context is omitted.
  App observations show their age and expire after 15 seconds; mutation freshness gates are unchanged.
  It adds one static `neyvia` system-prompt section
  (at most 6,000 characters, identical every turn), fresh context at `prompt.context`, a state diff at `prompt.submit`,
  local deny-path and held-file rules, a stop gate (`classic.Stop`, Neyvia counts the blocks, two at most), an inbox for
  sessions Neyvia does not run, and batched reports (turn, checklist, edits, claims, plan limits, end). Every call to
  Neyvia races 2 s and passes through when Neyvia is slow or absent. Contract: plans/29 section A.
- `.mcp.json` + `mcp/neyvia_mcp.py`: for hosts without the mod. With the mod loaded the server lists no tools (no
  duplicates); set `NEYVIA_MCP=1` to get the tools from it.
- Neyvia side: `neyvia.claude.mods` (setting, default on), `neyvia.claude.runs` (what the mod reported).
  Plan-limits runs get `CLAUDE_CODE_PLUGIN_DIRS` while the setting is on.

## Discoverable backend tools

Use `tools_describe(name="neyvia.timer.start")`, then `tools_call(tool="neyvia.timer.start",arguments={...})`.
Earlier underscore tool aliases remain callable for compatibility, but their schemas are deferred.
`manual_run` and `manual_observe` inspect the validated nested tool list before execution and refuse chains outside PORTED.
Manual procedures preserve this plugin's file, shell and cross-provider exclusions.

| Area | Tools |
|---|---|
| Situation | `state`, `attention.list`, `notify`, `manual.index`, `manual.load`, `runtime.list`, `lab.state` |
| Manuals next | `manual.observe/project`, `manual.run/compile/compiled/script.run`, `manual.versions/frontier/patches/patch.apply/demote`, `manual.recovery.bind/recover`; nested execution stays inside this plugin's PORTED scope |
| Projects | `folder.list`, `folder.open`, `folder.create`, `project.create` |
| Chats | `session.new`, `session.rename`, `session.pin`, `session.move`, `session.archive`, `session.cluster` |
| Interface | `pane.show`, `view.layout`, `view.arrange`, `view.scene`, `view.float`, `view.theme`, `terminal.list`, `terminal.read` (read Paul's Neyvia terminals; never types) |
| Follow-ups | `schedule.create/list/cancel/after`, `watch.create/list/cancel` |
| Time | `time.now`, `time.budget`, `timer.start/read/lap/stop/list` |
| Missions | `mission.list`, `mission.create`, `mission.control` |
| PDF | `pdf.state/open/goto/search/highlight/extract_text/zoom` |
| Image Studio | `image.state/open/crop/resize/composite/export` |
| Awareness | `claude.runs`; `work.claim/release/list`, `impact`, `intent.checklist`, `plan.update` (model fills intent template and publishes/updates its checklist; no hidden model call) |

Every approval Neyvia already asks for (new project roots, write-mode chats, mission start, image export) still
goes to the person in Neyvia; the tool answers "waiting for approval" until they press Approve.

## Not ported, and why

| Tool(s) | Why |
|---|---|
| `image.generate` | Spends the Codex subscription's image provider; a Claude Code run should not bill another provider's plan. Use it from Neyvia. |
| `claude.mods` | The person's own switch for this plugin; an agent should not turn its own tooling on or off. |
| Approve / decline (`/api/ui/approve`, `/api/ui/decline`) | Approvals stay with the person. Never exposed to any agent. |
| `workspace.read/write/search`, `terminal.exec`, `web.search/fetch`, `preview.*` | Claude Code has its own Read/Edit/Bash/WebFetch under its own permission rules; a second path would go around them. |
| `codex.plugins.*`, `codex.instructions.*`, `codex.prompts.read`, `codex.assets.*` | Codex's own assets and plugins; they belong to the Codex harness. |
| `semantic.*`, `context.*`, `orchestration.compile`, `skill.live.*`, `runtime.preflight/evidence/completion` | Internal machinery of Neyvia's native agent loop (receipts, memory, proofs); meaningless outside it. |
| `nas.*`, `laya.*`, `video.*`, `ui.inspiration.search` | Device transfer and native-runtime tools that need Neyvia's own agent context and grants. |
| Other `lab.*` actions | Native-agent Improvement Lab tools, not `neyvia.*` tools; only `lab.state` is shared. |

## Only a mod can do

- Report the live checklist and edited files as they happen, from inside Claude Code (no transcript polling).
- Claim files on the work board at the moment of the edit.
- Show Neyvia's connection in Claude Code's status line.

Ideas left for later (from `docs/research/claude-code-mods.md`): phone prompts via `$.prompt.submit`, a Neyvia pane
in the Code tab. Phone approvals through `tool.check` were left out on purpose: they would approve past `ask` rules.
