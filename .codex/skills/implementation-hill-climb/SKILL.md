# Implementation Hill Climb

Apply when the user wants substantial implementation and continuing improvement of its quality, efficiency, or reliability. Work on the actual product. Do not substitute a skill presentation, assessment-only handoff, scaffolding, or a stream of new ideas for authorized execution.

## Establish the working baseline

Recover the user's exact outcome, corrections, authority, model routes, release targets, and evidence requirements. Inspect the existing implementation and actual user path before replacing it. Preserve dirty work and make the current best candidate recoverable. Keep a compact task ledger of acceptance gates, known defects, current experiment, evidence, and next action. Explicitly distinguish existing, partial, integrated, and proven behavior.

Use the existing value-driven-improvement principles for honest comparison. Choose a practical baseline measurement for the user's actual friction: completion, fidelity, latency, token cost, startup, resource use, or required intervention. Do not claim a gain from smaller source files, fewer tools, or a passing build alone.

## Improve in complete increments

Choose a concrete bottleneck or missing outcome. State the causal hypothesis, smallest meaningful change, expected benefit, likely regression, and observation that would reject it. Investigate with targeted source reads, runtime evidence, and an appropriate existing solution check. More research should change the next decision.

Implement the full affected path, including state, callers, authority, errors, cancellation, recovery, and any required UI. Prefer reusing a working seam over introducing a second mechanism. Necessary difficult work is part of the task; neither complexity nor minimal line count is a goal.

Run the smallest checks that establish the claimed behavior. For a visible interaction, inspect it in the running product using the supported browser or computer tool. Read authoritative receipts and relevant logs. Repair an in-scope failure and rerun affected checks; broaden only when a new risk warrants it. Do not use Python tests or pytest. Artifact validators and production data-processing commands are distinct from test suites.

Compare like-for-like conditions, preserve adverse results, and keep the strongest verified candidate. If a hypothesis fails, diagnose the divergent transition and change the mechanism, representation, or experiment before retrying. Never weaken acceptance criteria, hide failures, or repeatedly tune on purported holdout cases.

## Integrate and simplify

The main agent owns the complete result, including the joins between independently developed pieces. Delegate only as authorized and with explicit ownership. For every capability, determine whether the user needs a control, explanation, correction, or inspection path. Reuse the existing start screen and Preview where appropriate. Remove or consolidate demonstrated redundancy only after checking dependencies and preserving necessary recovery, accessibility, and authority controls.

Inspect avoidable repeated work: context assembly, model calls, tool discovery, full snapshots, serialization, polling, and environment startup. Prefer a measured improvement with a preserved baseline over speculative optimization. Retain task-specific constraints through focus changes and continuation.

## Continue through the requested finish

Continue while acceptance gates remain unmet and a valid next step can improve the result. After the core works, pursue the highest-value justified refinement within the user's budget. Stop only at verified completion, an explicit budget boundary, or a concrete blocking condition; never call a partial programme complete.

Honor the latest user instruction about staging. If the user has authorized implementation and publication, carry the work through candidate verification, the exact GitHub target, recoverable deployment, and a check of the deployed revision and user journey. Do not reintroduce an earlier review stop the user has removed. A skill does not create additional authority.

Report outcomes and material limits briefly. Preserve detailed evidence in the task artifacts. Extract reusable lessons after a meaningful checkpoint under the user's learning policy, without delaying the useful result or silently editing personal memory.
