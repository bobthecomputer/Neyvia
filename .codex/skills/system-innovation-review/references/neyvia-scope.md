# Neyvia system scope and user corrections

Use this reference for the Neyvia harness programme discussed with Paul. It records product direction, not evidence that the runtime already implements it. Later user corrections take precedence. It grants no publication, memory, delegation, or external-effect authority.

## Main-chat understanding and creation

Sparse prompts should benefit from useful questions, concrete contrasts, and varied substantive directions in the normal conversation. Use clarify-and-create where appropriate. Preserve ambiguity until resolved or explicitly assumed. An advisor is optional and consumes the established brief when selected; no advisor page is required to get useful creative work. Prove late answers and corrections attach to the right task.

## Eight system initiatives

1. **Task-specific context.** Reuse Preview and the existing situation interface. Start with focused representations and deferred tool descriptions. A newly generated UI is optional and must justify its extra calls, latency, and complexity. Do not imply that a compact view improves total token cost without measuring the complete transport.

2. **Capability assembly.** Extract reusable operations after the task or at a useful checkpoint, under the selected learning policy. Preserve original tool authority, inputs, preconditions, verification, and recovery. Active-task repairs remain allowed. Distinguish a saved recipe from an enabled, reliable operation.

3. **Rehearsal and evaluation.** Expose these as opt-in personal experiences, with budgets and meaningful controls. They must not become an obligatory extra workflow. Separate ordinary verification from optional comparative experiments, and true isolated execution from a simulation of external effects.

4. **Working context and continuation.** Audit existing working memory and situation/compaction integration before adding another store. A continuation must retain the user's objective, decisions, unresolved obligations, and retrieval paths. Attach small scoped experience files by identity. Prove retrieval and use by a later agent; file creation alone is insufficient.

5. **Selective observation.** The model or declared task chooses focus and required facts. The runtime tracks the corresponding read dependencies, stable identities, revisions, events, and freshness policy. Refresh affected dependencies on known changes; use bounded polling when events are unavailable. Unknown coverage, expired observations, navigation, or ambiguous identity require broader reobservation before consequential action. Pixel-only surfaces may need fresh images; do not claim precise change tracking where the adapter cannot provide it. A deterministic invalidation rule needs no extra model call, but relevance prediction beyond that rule must disclose its model/heuristic and cost.

6. **Executable self-questioning.** Represent unresolved questions with the evidence needed, proposed inspection or experiment, and stopping condition. Reuse shared working state and experience notes. Ask the user for missing preferences or required decisions; use inspection/computation for discoverable facts. Mark observed evidence, inference, and unresolved uncertainty separately. Track whether an investigation changed a decision, rather than optimizing question count. API-visible reports are not access to hidden model reasoning.

7. **Common application and tool contracts.** Apply discoverable inputs/outputs, object identity, state events, authority, verification, and recovery to preinstalled tools and built-in capabilities as well as marketplace apps. Inventory each adapter and its unsupported boundaries. User and agent interactions must reconcile through the same production state. Preserve native installations and compatible environments when reuse is possible; a WASM wrapper cannot make arbitrary installed software portable.

8. **Measured interface improvement.** Inspect existing evaluation and improvement-lab work before adding more. Compare representations on like-for-like tasks, exact model routes, outcome quality, interventions, errors, total cost, and latency. Keep held-out work untouched where generalization matters and retain adverse outcomes. An optional evaluative workspace can expose these experiments; ordinary users should receive a coherent default experience.

## Review output

For every in-scope initiative, record current implementation boundary, missing integration, user control or deliberate automatic behavior, acceptance journey, important failure case, and expected resource impact. Keep evidence on demand in the existing product surfaces. Prioritize shared runtime improvements; specialist science or healthcare work belongs in an app unless the user changes scope.
