# Neyvia UI and desktop review — 2026-09-23

## Intended product

Neyvia is a personal agent workspace for starting work, building and trying apps, supervising orchestration, and operating browser, computer, phone, and other connected environments. The immediate usability goal is that a new task starts in the selected mode with one obvious composer, visible model/runtime/effort choices, an editable system prompt, and an inspectable result. Durable preferences and receipts should carry forward without pretending that behavioral memory changes model weights.

## Source changes in this review

- Agent keeps the composer in the first mobile viewport by showing two initial examples and a reversible **More starting points** control. Desktop start no longer has a horizontal scrollbar.
- Orchestration opens with its own heading and four orchestration examples. Preview state from an empty Workbench no longer leaks into a new Builder start.
- Workbench with an open preview now keeps its heading and composer visible at 1120 × 780. Its empty preview has a single concise title, and additional examples are optional.
- The composer prompt menu has **Edit system prompts**. It opens Settings → Rules & Routing with the correct URL; role prompts are editable and Save role is available. Settings category navigation now persists in the URL across reloads.
- A compact **Updates** control sits at the top right of desktop Agent modes and opens the actual Settings → Updates tab.

Changed UI source: `web/src/neyvia/NeyviaShellSurfaces.jsx`, `NeyviaWorkspace.jsx`, `NeyviaShell.jsx`, and `neyviaProductFinish.css`. The rebuilt `web/dist` contains these edits. This review preserved the checkout's earlier dirty App Factory, memory, Laya, and backend work.

## Chat attachments and current Laya check

The Agent composer now shows an explicit **Attach file** action and a removable file chip. A selected file can be sent with an ordinary chat turn. The browser sends bounded file bytes; the backend validates the name, MIME, declared size, base64, count, and limits, stages the bytes in the execution workspace, supplies the path and hash to the selected runtime, and removes the temporary files afterward. It persists file names, MIME types, sizes, and hashes with the user turn, not the file bytes. Failed turns retain the draft and selected files for correction. Orchestration still says attachments are unavailable for that route.

In the isolated local web app, the operator selected `attachment-probe.txt`, saw its file chip, sent a prompt that did not contain the file-only token, and Neyvia Native returned `cedar-419` from the file in a completed 58-second turn. A malformed-base64 backend request returned HTTP 400 before runtime dispatch. The final source and web build passed Python syntax, Vite build, and `git diff --check`. See `proof/ui-review-20260923/chat-attachment-journey.json` for the exact boundary; the latest metadata-only backend addition was not in the already-running server during that successful turn.
